# Mouse subscription root cause, fix and automatic pairing — hardware record 2026-09-27

Operator authority: the user granted flashing, serial commands and Windows remove/re-pair in this session. Agent-run hardware session on WINSTONDESKTOP (Windows build 26200). The ESP32-S3 was on COM10 (native USB, VID_303A PID_1001) at address `7C:4F:AD:21:52:89`. Raw logs, pairing JSON and hashes: [hardware-2026-09-27/manifest.json](hardware-2026-09-27/manifest.json). ELF files stay locally under ignored `build/<build>-out/`; their hashes are in the manifest.

## Root cause (fact, source plus hardware)

Arduino-ESP32 3.3.12 `BLEService::addCharacteristic` (`libraries/BLE/src/BLEService.cpp:260-274`) looks up a new characteristic by UUID. Under NimBLE, if one already exists it only resets the old one's `m_removed` flag and never adds the new object to the service map. `BLEService::start()` builds the GATT table from that map, so a second HID input report (same UUID 0x2A4D) never exists on the air. `BLEHIDDevice::inputReport(2)` still returns a valid-looking pointer.

- `diag1` build (split source plus observation-only logging, no fix): `[DIAG] report value handles: keyboard(ID1)=29 mouse(ID2)=65535`, meaning the mouse report was never registered.
- This fully explains `keyboard_sub=yes mouse_sub=no`: Windows had no mouse report characteristic to subscribe to.
- The earlier stale-GATT-cache hypothesis was not the cause. Windows held no pairing for the ESP32 when this session started.

## Fix (within approved core, backend and report interface)

`firmware/BLEScanner_WORKING_v7/hid_core_workaround.cpp` creates the mouse input report exactly as the core's `inputReport()` does: UUID 0x2A4D, READ|NOTIFY, and Report Reference `{0x02, 0x01}`. It inserts the report into the HID service's characteristic map using the standard C++ explicit-instantiation access idiom. There is no core edit, no report-map byte change and no payload change.

- `diag2` build: `keyboard(ID1)=29 mouse(ID2)=33`.
